# AGENTS.md

VS Code extension ".NET Testing+": loads a Visual Studio `.playlist`, runs those tests per project via `dotnet test <csproj> --no-build`, shows them in a custom "Playlist Tests" view inside the Testing panel. TypeScript, single package.

## Commands

- `npm run compile` — tsc to `out/`
- `npm run lint` — eslint; must pass before packaging
- `npm run harness --silent` (after `npm run compile`) — the **checked-in** verification harness in `harness/diagnostics.js` for run diagnostics (lossless chunks, retention, artifact pagination). It stubs `require('vscode')` via `Module._resolveFilename` and runs against `out/`, no dotnet needed. Unlike the throwaway harnesses below, this one is kept: re-run it after touching `src/runDiagnostics.ts`, `src/logger.ts` or the chunk-capture path.
- Package: `npx --yes @vscode/vsce package --allow-missing-repository` (keep `dummy-mes/**` and `harness/**` in `.vscodeignore` — they're local dev data and must not ship in the VSIX)
- Install: `code --install-extension dotnet-testing-plus-<version>.vsix --force`
- Apart from the diagnostics harness above, there is no test suite. Other verification is done with throwaway Node harnesses: stub `require('vscode')` via `Module._resolveFilename` (see deleted `vscode-stub.js` pattern), run against the real WSL data below, then delete the harness files.

## Version bumping

Every change that requires recompiling the project should bump the version (in `package.json` **and** the hardcoded version in the activation `log(...)` string in `src/extension.ts` — they have drifted before). Before proceeding, confirm with the user. Never bump the version without explicit approval.

- New feature → bump the minor (X.Y+1.Z).
- Bug fix or minor change → bump the patch (X.Y.Z+1).
- Neither → ask the user which to bump.

## Release checklist

1. Bump `version` per the version-bumping rules above (both locations).
2. `npm run compile && npm run lint`
3. Package, install, delete older `*.vsix` files.
4. If asked to publish, use the `VSCE_PAT` env var specified in `.env`, when such file exists. Never publish without explicit approval.

## Architecture

- `src/extension.ts` — state machine: solution resolution → discovery (`dotnet test --list-tests` + source scan) → playlist match → tree build. **Discovery is scan-first** (`dotnetTestingPlus.discovery.preferSourceScan`, default on): `discover()` paints the tree from the scan before spawning any `dotnet` process, so loading a solution never waits on MSBuild; the test-host listing is *confirm-only* and runs only from cache or, when `canSkipBuild` attests the binaries, with `--no-build`. `session.verifiedTests` holds the FQNs a listing confirmed (`verifiedFromListing` upgrades a test only when its bare name maps to exactly one scanned FQN), and `knownTests` = scan ∪ listing. Provenance is exposed as `verified` on `ControlApiTest` and `ScreenshotTest`. Context keys `dotnetTestingPlus.*` gate the view/title buttons and run-all enablement. Runsettings loads the default `.runsettings` next to the solution by default, with custom files selectable at any time or restorable via "Use Default File". Overrides are always active and solution-specific (persisted in workspaceState per session). When switching runsettings files or loading a solution, permanent overrides remain while non-permanent overrides update to the file's values. The default file is re-detected via `findDefaultRunsettings` on every activation (no cached path — a window refresh/folder change must not keep stale references). `activeFilter` holds the session-only test filter. The full tree is built **once** from all known tests (`showAllTests`), grouped by project via the source scan's FQN→csproj map; loading a playlist only **prunes** that tree (`filterTree`), never rebuilds it (`treeIsPruned` tracks when a restore is needed).
- `src/solutionDiscovery.ts` — runs `dotnet test <sln> --list-tests --nologo -v q --tl:off`; retries 3× on ENOENT (remote PATH may not be ready at activation); strips ANSI; parses bare names. `discoverSolutionTests(..., noBuild)` appends `--no-build`, used when reconciliation happens against binaries this window has seen built.
- `src/sourceScan.ts` — **fallback** scanner (used when the tree-sitter runtime or its WASM assets are unavailable). Regex scan builds bare-name→FQN index, FQN→file/line locations, **and** FQN→owning-csproj mapping. Always run the active scanner during discovery, even on cache hit (it's fast; the cache in `src/cache.ts` only skips the slow `dotnet --list-tests`). Also owns the shared directory walk (`walkCsFilesAsync`) and the `<Compile Remove>` / `<Compile Include ... Exclude>` reader (`parseCompileExcludes`, `isExcludedFromCompile`, `readCompileExcludes`): the walk is directory-based, so without it a `.cs` file removed from the project still parses as a test (19 FQNs on MES). Glob subset: `**` spans directories, `*`/`?` within a segment, case-sensitive, backslash-normalised; `$(...)` patterns are skipped and logged once. Test markers (MSTest `TestMethod`/`DataTestMethod`, xUnit `Fact`/`Theory`, NUnit `Test`/`TestCase`/`TestCaseSource`) live in `src/testAttributes.ts`; the regex interpolates them, so edit that file, not `METHOD_RE`.
- `src/astScan.ts` — primary scanner driver: walks solution projects, extracts test methods per file (tree-sitter `web-tree-sitter`, WASM), and folds them into the three maps with the identical FQN contract (`namespace.innermostclass.method`; file-scoped namespaces do **not** wrap their declarations in the grammar — a class after `namespace X;` is a compilation_unit sibling, so the walker tracks sibling order). **Incremental**: unchanged files reuse their cached extraction — no read, no WASM parse; the parser itself initializes lazily on the first extraction miss, so a fully-cached window reload never initializes WASM. Project `<Compile Remove>`/`Exclude` patterns are applied to the walk output *before* `seen`/prune bookkeeping. The parse/fold loop yields to the host every 8 ms (`YIELD_BUDGET_MS`) — a file is the finest granularity because `parser.parse` is synchronous; the residual stall is a single multi-megabyte file (~520 ms for 1.36 MB), so worker threads are the only further fix and are deliberately not used. The scan store lives in `src/fileScanCache.ts` (`<globalStorage>/scan-cache.json`) — **bump `AST_VERSION`/`REGEX_VERSION` whenever extraction logic or `TEST_ATTRIBUTES` change**; they key both the scan and solution caches (note the cascade: a bump also invalidates every `SolutionCache` entry via `parserVersion`). WASM lives in `assets/wasm/` (`tree-sitter.wasm` from web-tree-sitter, `tree-sitter-c_sharp.wasm` grammar ABI 15 — e.g. `npm pack tree-sitter-c-sharp@0.23.5`); regenerate both when upgrading `web-tree-sitter` so ABIs stay in sync.
- `src/fileScanCache.ts` — per-file scan cache: `ExtractedMethod`/`FileExtractor` contract shared by both scanners, the `foldMethods` first-wins fold helper, `contentHash`, and the persistent `FileScanCache` store (dirty-tracked whole-map write; memory-only when no storage dir). **Content-addressed**: `files: path → {mtime, size, hash}` plus `content: hash → {version, tuples}`, persisted as `{schema: 2, ...}` (an older/unreadable schema starts empty rather than migrating). Two tiers: unchanged mtime+size serves without reading; changed stat reads and hashes, and reuses the extraction when those bytes were seen at any path — that is what makes another worktree/branch checkout warm. `prune` garbage-collects unreachable content records.
- `src/solutionParser.ts` — parses `.sln`, `.slnf` and `.slnx` via `parseSolutionFile` (returns `{ projects, cacheDependencies }`; for a `.slnf` the base `.sln` is a cache dependency). `.slnf` projects are matched case-insensitively against the base solution's absolute paths.
- `src/testRunner.ts` — first builds the solution once, then runs tests per owning project with `dotnet test <csproj> --no-build --filter ...` so only the relevant test project(s) are executed. Batches are per-project, split **only** so each `--filter` argument stays under 30,000 chars (OS command-line limits; typical projects run as a single invocation — the fixed `dotnetTestingPlus.chunkSize` setting was removed). Two live result channels: a bundled VSTest logger streams per-test JSONL (see below) and per-project TRX files are parsed as they stream (see gotchas). Cancellation listens to **both** the profile-handler token and `TestRun.token` — the Test Results view's cancel button only fires the latter (it cancels a single task, never the profile token). `request.exclude` is honored at **every** tree level: VS Code excludes the top-most hidden nodes (whole class/project subtrees) when the explorer filter hides them (e.g. "Show only failed tests"); excluded tests are left untouched (not run, not marked skipped). `__readTrxForTest`/`__processLineForTest`/`__reportStreamedLineForTest`/`__collectTestsToRunForTest`/`__batchByFilterLengthForTest` exports exist only for harnesses. When debugging (`VSTEST_HOST_DEBUG=1`), the vstest testhost injects a `Debugger.Break()` right after attach; the `dotnetTestingPlus.skipPreBreakpoint` setting lets the extension auto-continue that first stop.
- `logger/` — C# source of `Playlist.TestLogger.dll`, a VSTest `ITestLogger` (FriendlyName `playliststream`) that appends one JSON line per test to `$PLAYLIST_STREAM_LOG` as each test finishes. The built DLL is checked in at `assets/logger/` and packaged into the VSIX; `testRunner.ts` passes it via `--test-adapter-path` and tails the JSONL file. Rebuild after editing (needs dotnet; from Windows use WSL): copy `logger/` to a WSL dir, `dotnet build -c Release`, then copy `bin/Release/netstandard2.0/Playlist.TestLogger.dll` back to `assets/logger/`.
- `src/testFilter.ts` — parses the custom filter (the native Testing search bar matches labels only and cannot be extended with `class:` syntax; tree rows can't host text inputs, hence the webview). Expression grammar, spaces insignificant: `|` ORs, `&` ANDs (tighter precedence), `!` negates (`!testName`, `class:!className`, `project=!projectName`), parentheses group, and juxtaposed terms are implicitly AND-ed (so old space-separated filters still work). `class:`/`project:` qualify a term, or a parenthesized group when placed before `(` (distributes; inner qualifiers override); unqualified terms match test name. The parser is tolerant (empty operands/stray parens dropped). The webview posts `filter` messages (debounced 300 ms) → `applyFilterInput` in `extension.ts`; applied to entries right before `buildTree` in `matchPlaylist`/`showAllTests`. Run All/Debug All run only the filtered (visible) tree.
- `src/runsettingsManager.ts` — auto-picks `.runsettings` next to the `.sln` (priority: `<SlnName>.runsettings` → `default.runsettings` → any); parses the XML into overridable values/parameters and materializes an overridden copy into extension storage.
- `src/codeLens.ts` — "Run Test"/"Debug Test" CodeLens for `csharp`. Lenses are derived from each session's (pruned) `treeRoot`, so tests hidden by playlist/text/result filters have no lens. `renderTree` fires the provider's change event only when a tree is actually rebuilt, not on per-result updates.
- `src/coverage.ts` — Cobertura (`--collect:"XPlat Code Coverage"`) → VS Code native coverage. The Coverage run profile calls `runWithSolutions`; coverage and debugging are mutually exclusive (debug wins, coverage silently skipped with a status-bar note). Reports are collected per project after its batches (mtime ≥ run start), merged per source file across reports, details cached on the `FileCoverage` (WeakMap) for `loadDetailedCoverage`, and the XML files deleted like TRX. Requires `coverlet.collector` in the test project.
- `src/runDiagnostics.ts` — file-backed **run diagnostics** (no `vscode` import, so `harness/diagnostics.js` tests it directly). Each `runChunk` and each solution build stages a `RunCapture` (temp dir, `fs.writeSync` per chunk — never buffered in memory) holding `stdout.log`, `stderr.log`, `run.log`, `stream.jsonl`, `results-N.trx` and, at the end, `manifest.json`. Only a capture that did **not** pass (failed tests, errors, cancellations) is promoted into `<storageUri|globalStorageUri>/diagnostics/<runId>/`; a passing one is deleted, so green runs leave nothing behind and nothing is ever written into the workspace. `RunDiagnosticsStore` owns promotion, `planRetention` (count / total MB / age bounds, newest run never pruned), `list`/`manifest`/`readArtifact` (paginated, allowlisted by the manifest, UTF-8 boundary-aligned) and `clear`. `previewChunk`/`formatChunkPreview` back the self-describing log truncation (see `logger.ts`).
- `src/logger.ts` — `.NET Testing+` output channel plus the capped in-memory **recent window** (`MAX_RECENT_LINES`, served by `GET /api/<session>/log`) — never treat it as the authoritative record. `logChunk(stream, text)` sends the full chunk to the active run capture, a 64 KB preview (or the text itself) to the channel and a 4 KB preview to the recent window, always with an explicit `N chars omitted; full text: <path>` marker. `setRunCapture` routes `log()` lines into the run's `run.log` and is set/cleared by `testRunner.ts`.
- `src/controlApi.ts` — the per-window **loopback data server** (`startLocalApi`): routes `/api/<session>/…` (session segment ignored; each window serves only its own data). Requires a per-election `x-internal-secret` header, because only the hub reaches it. Session-scoped routes are `state|events|log|runs|run|cancel|filter|screenshot`; `/runs/<runId>` serves a manifest and `/runs/<runId>/<artifact>` a paginated artifact page; solution-scoped routes are `<solution>/tests|code|playlist|select|runsettings`. Shared types (`ControlApiState`/`ControlApiTest`/`ControlApiHandlers`/`ControlApiRunsettingsAction`) live here.
- `src/apiHub.ts` — the shared **hub** (`startHub`) on `dotnetTestingPlus.controlApiPort`: serves the landing page `/` and `/<session>/`, `GET /api/sessions`, `/api/internal/ping` and `/api/internal/register` (secret-authenticated peer registry), and reverse-proxies `/api/<session>/…` (incl. SSE) to the owning window's local server. The hub is a pure router. Registry file `<globalStorage>/api-registry.json` = `{pid, port, secret}`; peer entries keyed by pid, evicted after 16 s of silence. `readRegistry`/`writeRegistry`/`pingHub` live here too.
- `src/apiCoordinator.ts` — `ApiCoordinator`: starts the local server, then elects a hub (probe registry → try to bind the port as the mutex → else join), heartbeats peers every 5 s, and takes over the port if the host dies. Exposes `state` (`{enabled, role: off|host|peer|error, sessionId, port, message}`), `broadcast`, and `refreshSolutions`. One instance per window; `stop()` is idempotent and drops the registry.
- `src/apiIds.ts` — URL ids: `sanitizeApiId` (lowercase, non-`[a-z0-9]` → `-`, trim), `deriveSessionBaseId` (first workspace folder, else workspace-file name, else `untitled`), `solutionIdFromPath`, `assignUniqueId` (collision → `-2`, `-3`, …). Reserved words (`api`, `internal`, `sessions`, …) are guarded so an id can never shadow a route.
- `src/webDashboard.ts` — the browser dashboard: **two** HTML templates with vanilla client-side JS. The hub serves `getSessionsLandingHtml` at `GET /` (one card per open session → `/<session>/`) and `getDashboardHtml(sessionId)` at `GET /<session>/`; the dashboard injects `SESSION_ID`/`API_BASE` and prefixes every relative fetch with `/api/<session>`. `loadTests()` fetches `/<solution>/tests` per non-loading solution and merges (each test carries `solutionId`). It is an **independent front end**: its search box is evaluated locally by a port of `src/testFilter.ts`'s grammar (**keep the two in sync**; verified by a differential harness), and its solution/test selection, result pills and `.playlist` reader never touch VS Code state. The bottom-bar `⚙ Runsettings` button opens a modal with one tab per solution (base-file dropdown + value/parameter overrides with reset/permanent-lock), driven by `GET`/`POST /api/<session>/<solution>/runsettings`. Live updates are push-only over `/events` (`state`/`testState`/`runStart`/`runEnd`) — never a WebSocket or polling loop: per-test events patch rows and the per-group `(X/Y passed)` counters via `refreshStatesInPlace` (coalesced to one repaint per 300 ms) instead of rebuilding the tree, `loadTests()` chooses an in-place repaint when only states moved (`canRefreshInPlace`) and a rebuild otherwise, a changed test inventory drives `loadTests()` from `state` events, and `EventSource.onopen` re-syncs after a dropped stream. `#emptyMessage` is a **permanent** element — `renderTests()` clears only `.solution-card` nodes — because `loadTests()` also writes to it: dereferencing it after the first render used to throw and silently kill every post-run refresh.
- `src/screenshot.ts` — builds the `ScreenshotSnapshot` tree (`solution → project → class → test`) shared by the VS Code webview preview (VS Code-scoped entries from `entriesForSession`) and the control API (`apiScreenshotSnapshot` in `extension.ts` scopes entries to the caller's FQNs, so a dashboard export is unaffected by VS Code's playlist/text/result filters).
- `src/skillInstaller.ts` — `dotnet-testing-plus.installAgentSkill` command ("Install Agent Skill...", also in the playlist view title's overflow menu below Show Output): two-step picker — scope (Global `~` recommended / Project workspace root / plus Windows-side global via `/mnt/c/Users/<user>` when the extension host runs in WSL and exactly one Windows profile is detected), then harness (Generic `.agents/skills` / Claude Code `.claude/skills` / OpenCode `.opencode/skills` project, `~/.config/opencode/skills` global / Codex `.codex/skills`). Overwrites on update so skill changes propagate.

## Control API (external automation)

The user-facing reference is the bundled skill `assets/skills/dotnet-testing-plus/SKILL.md` — **edit it first** when changing endpoints, then mirror any dev-relevant notes here (two copies exist; keep them in sync). Dev notes: every enabled window shares one API (`src/apiHub.ts` hub + `src/apiCoordinator.ts` election; see [Control API](/knowledge/architecture/control-api.md)). The hub binds `127.0.0.1` on `dotnetTestingPlus.controlApiPort` (default `48265`); peers run private ephemeral servers. Auth: optional bearer token (`dotnetTestingPlus.controlApiToken`) on `/api/*`; shared `x-internal-secret` for `/api/internal/*` and the hub→peer proxy. HTML: `GET /` (sessions landing) and `GET /<session>/` (dashboard). All data lives under `/api/<session>/…` with `<solution>/…` for solution-scoped routes (`tests|code|playlist|select|runsettings`); session-scoped routes are `state|events|log|runs|run|cancel|filter|screenshot`. `/api/<session>/log` stays the capped recent window; the authoritative full diagnostics are the retained runs under `/api/<session>/runs` (list), `/runs/<runId>` (manifest) and `/runs/<runId>/<artifact>?offset=&limit=` (paginated `{offset,nextOffset,eof,totalBytes,text}`), backed by `src/runDiagnostics.ts` and bounded by `dotnetTestingPlus.diagnostics.*`.

**Independence contract:** the dashboard and the VS Code UI are two independent front ends over one discovery/run core. They share discovered tests and run results, nothing else. VS Code's playlist/text/result filters and active tab must never reach the dashboard, and the dashboard's own search box, solution/test selection, result pills and playlist (a local `.playlist` reader) must never mutate VS Code state. So `GET /api/<session>/<solution>/tests` reports **all** discovered tests with their states, `POST /api/<session>/screenshot` takes an explicit `fqns` list, and only the VS Code-scoped endpoints (`POST /api/<session>[/<solution>]/playlist|filter|select`, `POST /api/<session>/run {"all":true}`) touch the tree. FQNs that belong to no loaded solution come back in `missing`. Sessions/solutions are addressed by sanitized ids (resolve via `GET /api/sessions`/`GET /api/<session>/state`); the raw paths are in the responses. From a Windows-side agent or browser, reach a WSL extension host via WSL2 localhost forwarding. Verify changes with `GET /api/sessions` → `POST /api/<session>/run` → poll `GET /api/<session>/<solution>/tests` (use `dummy-mes/MES.Dummy.sln`, never the WSL target, for local verification).

## dotnet / target-solution gotchas (verified against the user's WSL env)

- Target: a large multi-project solution in WSL; dotnet installed via `mise` (SDK 10.x).
- **Microsoft.Testing.Platform mode**: `dotnet test --list-tests` (and even `dotnet vstest --ListTests`) prints only **bare method names**, never FQNs. `-p:TestingPlatformDotnetTestSupport=false` does not help. This is why the source-scan mapping exists — do not try to "fix" list-tests.
- **`dotnet test` on a solution writes one TRX per test project next to that project** (`<proj>/TestResults/...`), ignoring any `LogFileName` directory. It emits a `Results File: <path>` line per project **as each finishes** — the runner parses each TRX the moment its line streams (live results). There are **no per-test `Passed/Failed` stdout lines**; don't try to parse them. Per-project test runs use the same TRX behavior but no longer trigger the "No test matches the given testcase filter" warnings because each filter targets the owning project.
- Paths: extension host runs in WSL (POSIX `/src/...` valid); Windows-side Node harnesses must use `\\wsl.localhost\<distro>\...`. Real paths may contain `/src/` twice — never blind-replace `/src/`.
- **Custom VSTest loggers**: the assembly filename MUST end with `TestLogger.dll` and `--test-adapter-path` must be a **directory** (a file path is silently rejected), otherwise vstest reports "Could not find a test logger". The `TestLoggerEvents` event is `TestResult` (not `TestResultHandler`). Custom loggers coexist fine with `--logger trx`. The streamed FQN is the real FQN (no bare-name problem).
- Never cache empty (0-test) discovery results; cached empty lists are treated as invalid.

## VS Code API constraints

- `TestController` trees can only live in the Testing view. The own-tab requirement is solved with `contributes.views` under the existing `"testing"` container: tests show **only** in the native Test Explorer, and the custom `playlistView` sub-tab is a `type: webview` view holding the filter box, playlist/runsettings rows, and the skip-pre-breakpoint toggle. Operational buttons (solution select/switch, stop loading, refresh, show output) are `view/title` contributions scoped to `view == dotnet-testing-plus.playlistView` (so their icons appear in the Playlist Tests tab's title bar, not the Test Explorer's).
- The native Testing search bar matches only `TestItem.label` (glob-aware, `!` negation) plus exact tags via `@ctrlId:tagId`; extensions cannot hook it — hence the custom filter command.
- TreeView has no double-click event; item `command` fires on click. Go-to-source is a click, not a double-click.
- `TestItem.uri` is readonly per old `@types/vscode` typings — a cast is used in `testTree.ts`.

## Editing hazards

- `src/testRunner.ts` `ANSI_RE` contains a **literal ESC byte (0x1B)** before `\[` — string-replacement edits that include that line will fail to match, and eslint needs the `no-control-regex` disable comment above it.
- `src/sourceScan.ts` regexes are deliberately shaped: `CLASS_RE` is anchored at line start (the word "class" appears in comments/strings and once silently dropped a test), `METHOD_RE` tolerates combined attributes (`[TestMethod, TestCategory(...)]`) and all `class` bodies are scanned (partial classes split `[TestClass]` and methods across files). `METHOD_RE` is interpolated from `src/testAttributes.ts` — add new framework markers there, and re-run a harness against the fixture/target solution either way. The AST path (`src/astScan.ts`) is behavior-checked against the regex path by harness before release.
- The repo owner hand-edits files between sessions (versions, commands, context keys). **Always re-read a file before editing it.**
